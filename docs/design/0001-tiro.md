# Tiro — design

> Marcus Tullius Tiro, Cicero's secretary, is credited with *notae Tironianae*,
> the Roman shorthand used to take down speech as it happened.

**Status:** draft, 2026-10-17. Owner: dhk. Issue: #1.

## 1. Problem

Conversations get captured in many places, by different tools, in different shapes:

| Source | Shape | Reach |
|---|---|---|
| Wispr Flow | Transcript + summary, sometimes linked to a calendar event | MCP (`search_meetings`, `get_meeting`, `get_meeting_by_calendar_id`) |
| Gemini (Google Meet) | Summary email from `gemini-notes@google.com` + "Notes by Gemini" Doc attached to the event | Gmail, Drive, Calendar attachment |
| Zoom | AI meeting summary + VTT transcript | Zoom API, **meetings the owner hosts only** (see §10) |
| Teams, Otter, other vendors | Recap email | Gmail |
| iPhone | Voice Memo + on-device transcript | File dropped into a Drive/Dropbox folder |
| ChatGPT | Session transcript | Paste or export file |

None of them knows about the others. None reliably knows **who was actually
there**, and none tracks **what happened to the follow-ups**. Off-the-shelf
notetakers (Granola, Fireflies, Otter, Fathom) each pull together the
recordings *they* made. None ingests other tools' output and anchors it to the
calendar.

## 2. Scope

Tiro does one thing: **figure out conversations.** For each conversation:

1. Did it happen? When, and for how long?
2. Who was actually there?
3. What was said? (the raw sources, kept verbatim)
4. What was the gist? (a summary you have confirmed)
5. Who owes what to whom? (action items you have confirmed)

**Not in scope:** what a conversation *means* for a relationship or a goal,
outreach drafting, briefs, scoring people. That is wingman's job. Tiro is the
factual record; clients interpret it.

## 3. Evidence from the 2026-10-10..17 pilot

A read-only pass over one week of calendar + Wispr + Gmail. It shaped every
rule below. Details: [the pilot snapshot](../snapshots/2026-10-17-pilot-week.md).

- **Capture coverage was 4 of 14** real conversations. Two Zoom calls left
  nothing in Gmail. Coverage, not summary quality, is the bottleneck.
- **Duplicate events for the same call.** The owner blocks time (2:00, no
  attendees); the other party sends their own invite with the link (2:15,
  Zoom). The owner reports this is common.
- **Unlinked recording overlapping two events.** A Wispr recording (9:33–9:50,
  `attendees: []`) overlapped event A (9:15–10:05) and event B (9:30–9:55,
  created that morning). The assistant guessed a third person from the
  transcript content and **was wrong**. It was B, the closest-fitting event.
  Lesson: a participant is never inferred from content.
- **Summaries mix up who owes what.** One Wispr summary put all 6 next steps
  under "Speaker 2", including ones its own body says were the owner's. Gemini
  filed an item under the guest that reads as an ask *of* the owner.
- **Recording with no event.** A 2-hour coaching check-in (Wispr) matched
  nothing on the calendar.

These echo wingman RFC-073's incidents: invite attendees ≠ people who spoke,
and model summaries misattribute what was said.

## 4. Data model

```
Conversation
  id
  status            scheduled | happened | no_show | rescheduled | cut_short | unrecorded
  window            {start, end}           # actual, if known; else scheduled
  events[]          calendar event ids     # >1 when duplicates were merged; one is primary
  participants[]    {email?, name, role: owner|guest, confirmed: bool, source: invite|user|speaker_label}
  sources[]         Source
  summary           {text, tier: endorsed, confirmed_at} | null
  action_items[]    ActionItem
  anomalies[]       {kind, question, resolved_by?, resolution?}

Source                                      # immutable once stored
  kind              wispr | gemini | zoom | otter | teams | voice_memo | chatgpt | other
  external_id       vendor's id (meeting id, Gmail message id, file id)
  url               link back to the original
  captured_window   {start, end} as the vendor reports it
  transcript?       verbatim text                     tier: observed
  vendor_summary?   vendor's own summary, verbatim    tier: observed (as a quote of the vendor)
  speaker_labels[]  as the vendor emitted them ("Speaker 1")

ActionItem
  text
  owner             participant ref | unknown
  counterparty?     participant ref
  due?
  state             proposed | confirmed | rejected | done
  todoist_id?
  source_ref        which Source + offset it came from
```

Tiers follow wingman RFC-073: **observed** = verbatim from a source;
**endorsed** = a model draft the owner confirmed. Nothing unconfirmed is ever
promoted out of `proposed`.

## 5. Matching a capture to the calendar

Run per capture, in order:

1. **Vendor link wins.** The source carries a calendar event id (Wispr
   `get_meeting_by_calendar_id`, Gemini Doc attached to the event) → attach.
2. **Closest-fitting overlap.** Score every event that overlaps the capture
   window by fit: fraction of capture inside the event × fraction of event
   covered, plus a bonus for an event created the same day. Exactly one
   candidate → attach, still unconfirmed. More than one → anomaly `ambiguous_event`,
   best fit offered first.
3. **No overlap** → anomaly `no_event` ("Who was this with?").

Participants from the invite start as `confirmed: false`. The owner confirms or
corrects them; speaker labels are mapped to people only by the owner.
**Tiro never assigns a participant from transcript content.**

## 6. Merging duplicate calendar entries

Auto-merge without asking when all hold:

- Starts within 30 minutes of each other and windows overlap.
- One event is owner-created with no other attendees (a time block).
- The other has an external organizer or attendees, or a conference link.

The event with real attendees/link becomes primary. A capture linked to
**either** merged event belongs to the merged conversation, whichever one the
vendor happened to link it to. Two overlapping events
that **both** have other people are never merged. That is the ambiguous case
in §5 step 2.

## 7. Anomalies: ask only when something looks off

| Kind | Trigger | Question & answers |
|---|---|---|
| `maybe_no_show` | Event with other attendees + conference link, no capture **2 hours after the scheduled end** (captures lag: the pilot's Gemini email arrived about 50 min after the call) | "Did this happen?" Yes / No-show / Rescheduled / Happened, not recorded |
| `maybe_cut_short` | Capture duration < 50% of scheduled | "Cut short?" Yes / Ended early as planned / Recording missed part |
| `no_event` | Capture overlaps no event | "Who was this with?" (people picker; optional title) |
| `ambiguous_event` | Capture overlaps >1 non-mergeable event | "Which one?" best fit first |
| `owner_unclear` | Action item owner is a speaker label or contradicts the body | "Whose is this?" |

In-person events with nothing captured (no conference link) are expected and
get one batched end-of-day/week "these happened?" check, not individual
alerts. Answers are stored on the anomaly, so the same question is never asked
twice.

## 8. Interface (MCP server)

Read:

- `conversations(since, until?, person_email?, status?)`
- `conversation(id)` → events, confirmed participants, sources, summary, action items
- `interactions(person_email)` → chronological list: when, how long, gist, open items
- `open_action_items(owner?: me|them|any)`
- `anomalies(open_only=true)`

Write (each shows the exact effect and requires confirmation):

- `ingest(source_kind, payload|ref)`: for paste/upload sources (ChatGPT, files)
- `resolve_anomaly(id, answer)`
- `confirm_participants(conversation_id, participants[])`
- `confirm_summary(conversation_id, text)`
- `confirm_action_items(conversation_id, items[])`
- `push_action_items(conversation_id)` → Todoist; dry-run by default

Sync: `sync(since)` pulls from all configured adapters and runs matching,
merging and anomaly detection. Idempotent: `(kind, external_id)` is unique.

## 9. Wingman integration

Wingman is a client, the same way it calls woven (`woven_warm_path`):

- Wingman reads `interactions(email)` and `conversation(id)` for briefs and
  follow-up suggestions.
- `relationship_log` entries reference a Tiro conversation by `source_url`
  instead of copying transcript text.
- Identity crosses the boundary by **email** only. Wingman maps email →
  its own person record. Tiro never imports wingman's people model.
- Tiro never calls wingman.

## 10. Adapter build order

1. **Wispr Flow**: richest source; already linked to calendar events in most cases.
2. **Gemini**: Gmail `from:gemini-notes@google.com` + Doc attachment on the event.
3. Matching, merging, anomalies (§5–7) + confirmation flow.
4. Wingman client.
5. **Zoom**: meeting-summary and recording-transcript APIs. Both depend on the
   **host's** settings and account
   ([AI Companion API](https://developers.zoom.us/docs/api/ai-companion/),
   [transcript retention](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0076632)),
   so this adapter covers only meetings the owner hosts. For Zoom calls someone
   else hosts (both Zoom calls in the pilot), the only route is local capture
   (Wispr). Summaries are requested per meeting; whether Zoom also emails them
   to non-hosts is unverified.
6. **Voice Memos**: watched Drive/Dropbox folder.
7. **Vendor recap emails** (Teams, Otter, …): one Gmail parser per sender.
8. **ChatGPT**: `ingest` paste/upload.

## 11. Privacy

Transcripts contain other people's words. Tiro stores them for the owner only,
never shares them, and keeps raw sources out of any client response unless
asked for explicitly. Deleting a conversation deletes its sources.

## 12. Decisions and open questions

Decided (2026-10-17):

- **Storage: SQLite.**
- **`maybe_no_show` fires 2 hours after the scheduled end.**
- **Zoom:** API for meetings the owner hosts; Wispr for the rest (§10).
- **Vendor link to a merged duplicate:** either event counts (§6).

Open:

- Host process: run on lobster next to wingman, or somewhere else?
- Language: Python, to match wingman, unless there's a reason not to.
